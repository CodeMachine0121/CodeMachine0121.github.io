如果你是一名習慣了 RESTful API、關聯式資料庫與集中式錯誤處理的後端工程師，剛轉向 Web3 時，直覺可能會認為：「這不就是寫程式嗎？能有多大的區別？」

答案是：**區別巨大。** 在 Web2，你是在處理「輸入與輸出」；但在 Web3，你是在維護一個**「確定性狀態機 (Deterministic State Machine)」**，且必須維持全球共識。

### 1. 核心概念：什麼是確定性狀態機？
在傳統後端，如果伺服器當機，你可以重啟；如果交易失敗，資料庫有 `ROLLBACK` 機制。但在區塊鏈上，沒有「復原」按鈕。

智能合約本質上就是一個狀態機：
*   **狀態 (State)：** 存在鏈上的所有變數（例如 `balances[address]`）。
*   **轉換 (Transition)：** 每一筆交易 (Transaction) 都是一個指令，驅動合約從舊狀態轉換到新狀態。
*   **確定性 (Determinism)：** 這是最關鍵的點。**同樣的輸入，在網路上任何一個節點執行，都必須得到完全相同的結果。** 正因為如此，Solidity 無法處理「非確定性」的因素（例如亂數、或是直接發起外部 API 請求，這也是為什麼需要 Oracles 的原因）。

### 2. Web2 與 Web3 的三大思維衝突
在寫下第一行程式碼前，你必須先捨棄這些 Web2 的習慣：

*   **程式碼即資料 (Code is Data)：** 在 Web2，邏輯（App）與資料（Database）是分開的。在 Solidity，你的程式碼直接定義了資料儲存的結構 (Storage)，而這些資料一旦上鏈就永久存在。一旦部署，修改儲存結構（Storage Layout）是非常危險且複雜的。
*   **沒有「熱修復」這回事：** Web2 的 Bug 可以隨時修復上線。但在 Web3，代碼即法律 (Code is Law)。在 Production 環境中的 Bug 就是駭客的提款機，且通常無法修復。
*   **Gas 是新的效能指標：** 在 Web2，你優化 CPU 與記憶體使用率；在 Solidity，你優化的是 **Gas**。每一個變數型別（`uint8` vs `uint256`）、每一行記憶體讀取，都直接影響使用者的成本與網路擁塞程度。

### 3. 為何我們需要深入理解這些概念？
開發 DeFi 協議或是複雜的鏈上金融應用時，這不是在練習寫 CRUD，而是進行「金融工程」：
1.  **零容錯率：** 鏈上資產一旦因為合約漏洞流失，往往無法追回。
2.  **治理與權限：** 所有的狀態變更都必須具備嚴格的權限控管與治理流程，這要求開發者對權限架構有極深的理解。
3.  **架構可擴展性：** 考慮到協議未來的升級需求，如何設計合約架構（如 Proxy 模式）同時確保狀態遷移的安全性，是每個專業合約開發者的必修課。

若你還沒開始，請務必安裝 [Foundry](https://book.getfoundry.sh/)，這是目前業界最主流且功能強大的開發框架：

```bash

curl -L https://foundry.paradigm.xyz | bash
foundryup

# 初始化專案
forge init web3-learning-journey
cd web3-learning-journey
forge test
```

### 思考題：
假設你要設計一個功能，讓合約執行轉帳給外部合作夥伴。在 Web2，你只需檢查資料庫的權限並發起 API 呼叫；**在智能合約中，你要如何確保這個狀態改變是「已授權」且「不可逆」的？你認為在設計這類合約時，最該優先防範的風險是什麼？**
