## 系列主軸：用工程思維進入交易，而不是用直覺

這個系列的讀者設定很明確：**會寫程式、但完全沒有交易基礎的軟體工程師**。它不教你怎麼賺錢，教的是怎麼把「交易」這件事拆成一個你熟悉的東西——一條資料管線、一組可測試的函式、一個會失敗會重連的線上服務。

主軸是三個工程師本來就有、但交易圈普遍缺乏的能力：

- **自動化**：人看盤會累、會漏、會情緒化；程式不會。凡是重複的判斷，都能寫成程式碼。
- **防禦性設計**：交易程式跑在真錢上，斷線、限流、資料缺漏、極端行情都會發生。工程師習慣先想「它會怎麼壞」。
- **數據分析**：策略好不好不是「感覺」，是可回測、可量化、可比較的。你已經有拿數據做決策的習慣。

反過來說，工程師進場最容易犯的錯也很固定：**把回測寫得太樂觀**（未來函數、忽略手續費與滑價）、**把指標算錯卻沒發現**（沒有對照組）、**把系統寫得太脆弱**（一次斷線就整包卡死）。這三件事會被拆進 Day 04–06（每個指標都要有對照組）、Day 20–21（把成本加回去、以及組合搜尋的統計陷阱）、Day 23（防禦性設計）專門處理，而不是最後才補一句提醒。

| 階段 | 名稱 | 這段在做什麼 | 天數 |
|---|---|---|---|

| 第一階段 | 基石：數據擷取與市場基礎 | 讀懂 K 線、把歷史資料抓下來存好，並實作 MA／EMA／RSI 三個入門指標 | Day 02–08 |

## 貫穿主線：一個真的會上線的交易機器人

全系列用**同一個**專案當主線，隨天數長大。每一天的產出都是這個專案的一個模組，不是各自獨立的玩具範例。

> **範例專案：`quantbot`——一個跑在 Binance 上的加密貨幣量化交易機器人，核心是一套讓使用者自己排列組合的策略積木庫。**
>
> **為什麼選加密貨幣**：市場 24/7 不休市（不用處理開盤收盤與跳空）、歷史資料免費且完整（不必先買資料源）、有官方 testnet 可以拿假錢跑真流程（不必第一天就冒風險）、REST 與 WebSocket 都有公開文件。這些條件讓讀者可以**當天複製當天跑起來**，這比選哪個市場更重要。
>
> **為什麼是積木庫、不是三個寫死的策略**：策略被拆成可互換的積木（進場條件、過濾條件、出場規則，Day 24 再加上部位計算），使用者用設定檔就能組出自己的策略，不必改 Python。系列裡的三個策略是**用來證明這套積木夠通用**的示範，不是產品本身。這個定位決定了 Day 16–22 整段的設計，也決定了 Day 21 那個安全鎖為什麼非有不可——能自由組合，就必須同時有能力判斷組出來的東西是不是垃圾。
>
> **專案的時間線**：Day 01 起手（環境與骨架），Day 02 抓到第一根 K 線，一路長到 Day 30 變成一個能自己擷取資料、計算特徵、產生訊號、控制部位、下單、回報狀態、出錯自己重連的服務。

### 技術棧（全系列一致）

| 用途 | 選型 | 為什麼不用別的 |
|---|---|---|
| 語言 | Python 3.12 | 量化生態系最完整；不是因為它快，而是因為算得快的部分可以交給 numpy／Numba |
| 歷史資料回補 | `data.binance.vision`（官方 public data dump） | 免費、不吃 rate limit、直接下載 zip；用 REST 翻頁抓一年份 1 分鐘 K 線要跑幾百次請求，慢好幾個數量級 |
| 即時連線與下單 | `ccxt`（統一介面）＋ 原生 `websockets` | 不自己手刻 REST signing；但即時資料走原生 WS 才控制得住重連與序號校驗 |
| 交叉驗證對照組 | CoinGecko API（免費 Demo 層） | 每個資料源都要有第二個來源對得起來，才知道自己沒抓錯 |
| 非同步 | `asyncio` ＋ `aiohttp` | 不用 threading——I/O bound 的爬取與行情訂閱是 asyncio 的主場 |
| 資料處理 | `pandas` ＋ `numpy` | 全系列**一律向量化**，NEVER 用 for loop 遍歷 K 線 |
| 儲存 | TimescaleDB（PostgreSQL extension）＋ `asyncpg` | 不用 SQLite／CSV：時序資料要的是 hypertable 分區、時間桶聚合與壓縮 |
| 指標 | 自己實作為主，`pandas-ta` 當**驗證對照組** | 教學核心就是「自己算一遍才知道哪裡會錯」；但每個指標都要跟現成套件對數字 |
| 回測 | `VectorBT` 為主，`Backtrader` 當對照說明 | VectorBT 是向量化的，跟前面的資料處理一脈相承；Backtrader 事件驅動、只當觀念對照 |
| 視覺化 | `Plotly`（互動圖表）＋ `matplotlib`（靜態） | 指標文一定要有圖，Plotly 可以縮放看細節 |
| 加速 | `Numba` | 遞迴型指標（EMA、RSI 的 Wilder 平滑）向量化不掉時才用 |
| 告警 | Telegram Bot API | 免費、有官方 API、手機直接收 |
| 設定與密鑰 | `pydantic-settings` ＋ `.env` | API key NEVER 寫進程式碼，NEVER 進版控 |
| 測試 | `pytest` | 指標與策略邏輯要有測試，尤其是邊界（資料不足、有缺漏） |
| 部署 | Docker ＋ Docker Compose ＋ VPS | 本機與雲端同一份映像檔 |

## 資料來源 Provider 版圖與選型

這是全系列的**選型基準文件**。Day 01 會把這張版圖攤開給讀者看，之後每一天用到資料時都要對得回這裡。

原則很簡單：**不同用途用不同 provider，但每一種用途只准有一個主來源。** 混用是災難的開始——不同家對「時間戳是開盤還收盤」「成交量是張數還是名目金額」「現貨還是永續」的定義不一樣，接起來會產生看起來很合理、實際上是假的訊號。

### 版圖：五類 provider 各自解決什麼問題

**A. 交易所原生（本系列的主力——所有進到 `quantbot` 的市場資料都源自這裡）**

| Provider | 拿什麼 | 條件 |
|---|---|---|
| `data.binance.vision` | 歷史批次：klines、aggTrades、bookTicker、fundingRate；daily 與 monthly 的 zip | 免費、無額度限制、不吃 API weight。當日資料隔日上傳，月檔次月初開始上傳 |
| Binance REST（透過 `ccxt`） | 近期缺口回補、帳戶與訂單查詢 | klines 單次上限 1000 根、每次 2 weight、每 IP 每分鐘 2400 weight |
| Binance WebSocket（原生 `websockets`） | 即時逐筆成交、掛單簿增量更新 | 免費；需自行處理心跳、重連與序號斷裂後重取快照 |

Binance 之所以是主來源，有三個可查證的理由，Day 01 要寫進去：市占（CoinGecko Q2 2026 報告，前十大 CEX 現貨總量 $1.95 兆中 Binance 佔 38.7%，第二名 Bybit 約 10%）、資料粒度（Binance 提供 1 秒 K 線，Bybit 與 OKX 最小只到 1 分鐘，這對第二階段的微觀結構特徵是實質差距）、以及官方免費 public data dump 的存在。

**B. 多交易所聚合（跨市場參考與交叉驗證）**

| Provider | 適合什麼 | 免費層現況 |
|---|---|---|
| CoinGecko API | 幣種清單、市值、跨交易所參考價、交叉驗證 | Demo 方案每月 10,000 credits、50+ endpoints，含最多 1 年的日／時／分 OHLCV |
| CoinMarketCap API | 幣種基本資料 | 每分鐘 50 calls、每月 15,000 credits，但**免費層不含歷史 OHLCV**（只有 price quotes），所以本系列不拿它當歷史資料源 |
| CryptoDataDownload | 免登入的 CSV 下載，涵蓋 Binance／Coinbase／Kraken 等 25+ 交易所，時間戳已對齊 | 免費。適合當「不想寫爬蟲的第二對照組」 |

**C. 機構級 tick 與 L2 歷史（本系列用不到，但要讓讀者知道存在與價位）**

| Provider | 定位 |
|---|---|
| Tardis.dev | 150+ 交易所的 tick 級掛單簿、成交、資金費率、清算、選擇權鏈；月費約 $50–900 |
| Kaiko | 機構級整合行情，合規導向 |
| CoinAPI | 統一 schema 的 REST 歷史查詢 ＋ WebSocket 歷史重播 |
| Amberdata | 機構級市場與鏈上整合 |

什麼時候才需要付這筆錢：要跨多家交易所重建多年份的 L2 掛單簿、或要做需要精確 bid-ask 的高頻策略時。本系列的策略頻率用 Binance 原生資料就夠，Day 01 要明講「你現在不需要買這個」，免得讀者以為入場門檻是每月幾百鎂。

**D. 衍生品專項（資金費率、未平倉、清算）**

CoinGlass 聚合 30+ 交易所的清算、未平倉量、資金費率，2026 已改版到 V4 API（新的 base URL 與認證標頭）。網站上核心資料免費看，API 存取與深度歷史需要 Pro。本系列主線是現貨，這塊放在 Day 30 的演化路徑（資金費率套利、用清算熱力圖當特徵）。

**E. 鏈上資料（本系列主線用不到）**

| Provider | 定位 |
|---|---|
| Dune | SQL dashboard，工程師最順手的介面 |
| Nansen | 錢包標記與 smart money 追蹤，覆蓋 20+ 條鏈 |
| Glassnode | 機構級鏈上指標（realized price、持有者分布、NVT） |
| Etherscan | 交易、餘額、合約驗證的基本查詢 |
| DefiLlama | 協議 TVL、DEX 成交量，API 免費 |
| The Graph | 自建 subgraph 索引特定合約事件 |

這塊沒有單一大宗，是分工不同。**要對讀者誠實：本系列 30 天沒有一天真的需要鏈上資料**——所有特徵（OBI、VWAP、Volume Profile、流動性擺盪）都來自交易所的行情與掛單簿。鏈上是 Day 30 演化路徑裡的一個方向，不是主線。Day 01 把它講清楚，是為了讓讀者不要一開始就被「要不要買 Nansen」這種問題卡住。

### 選型原則（每一天用到資料時都要對得回這幾條）

1. **先問「這筆資料要拿來做什麼決策」，再選 provider。** 決策不同，可接受的延遲、粒度與成本就不同。
2. **能用交易所原生就用原生。** 聚合商會重採樣、對齊、補值，這些加工在回測時是雜訊來源。更重要的是：你實際下單的地方就是那個交易所，訊號用的資料 **MUST** 跟成交場所一致。
3. **現貨資料 NEVER 拿去回測永續合約策略，反之亦然。** 兩者的價格、成交量、費用結構都不同，這是新手回測失真最常見的來源之一。
4. **歷史批次與即時串流是兩條路徑，分開設計。** 批次走 `data.binance.vision`，即時走 WebSocket，中間的缺口用 REST 補。三者的資料 **MUST** 在入庫時統一 schema 與時區。
5. **每個主來源都要有對照組。** 用 CoinGecko 或 CryptoDataDownload 抽樣比對 Binance 的資料，不一致就要查清楚原因再往下做。
6. **免費層夠不夠用，動工前先算。** 不要寫到 Day 20 才發現要付月費。本系列 **MUST** 保證讀者從頭到尾零成本跑完（testnet ＋ 免費資料源）。

### 第一階段｜基石：數據擷取與市場基礎（Day 02–08）
專案階段：從零到一條會自己跑的資料管線。這段有兩個目標——**手上有乾淨、完整、查得快的歷史資料**（Day 02、03、07、08），以及**用最經典的三個指標建立「自己算一遍並驗證」的習慣**（Day 04–06）。後面所有分析都建在這上面。

**Day 02（2026-09-16）— 打開行情圖只看到一堆紅綠棒子？先把 K 線（OHLCV）拆成熟悉的資料結構**
- 講什麼：K 線就是一個時間區間內的五個數字（開高低收量）；為什麼是這五個、各自代表什麼資訊、哪些資訊在壓縮過程中被丟掉了（這條伏筆在 Day 09 收）。時間框架的取捨：1m 資料量大但細節多，1d 乾淨但一年只有 365 根。
- 交易概念補課：K 線、OHLCV、timeframe、多空的意思。用「一分鐘內所有成交的 summary statistics」來解釋，工程師一聽就懂。
- 工程實作：常見的資料格式與陷阱——時間戳是毫秒還是秒、是開盤時間還是收盤時間、時區一律用 UTC、最後一根 K 線是「還沒收完」的（這是新手最常見的未來函數來源）。用 pandas 讀進來、設 `DatetimeIndex`、確認資料型別。
- 資料來源說明：今天只要**一小段**資料來看清楚結構，所以用最短的路徑拿——直接下載 `data.binance.vision` 的一個月檔就好，不解釋原理。「為什麼不是打 API、大量歷史該怎麼抓」是明天 Day 03 的主題，今天只需要手上有一張 DataFrame。
- 今日交付物：`quantbot/ingest/` 下一支腳本取得 BTC/USDT（現貨）的日線 K 線存成 parquet，並用 Plotly 畫出第一張 K 線圖。

**Day 03（2026-09-17）— 想抓一年份的行情資料，卻被 API 限流擋下來？別用 API，先把官方資料包整包載下來**
- 講什麼：這天要打破一個新手預設——「要歷史資料就去打 API」。實際算一次就知道行不通：Binance klines 單次上限 1000 根、每次 2 weight、每 IP 每分鐘 2400 weight，抓一年份的 1 分鐘 K 線要翻好幾百頁。正確做法是**兩條路徑分開**：
  - 大量歷史走 `data.binance.vision` 的 zip 批次下載（免費、不吃 weight、一次一個月）。
  - 只有「最近幾天、資料包還沒上傳」那段缺口，才用 REST 補。
  - 即時資料是第三條路徑，Day 09 才接 WebSocket。
- 交易概念補課：symbol 命名（BTC/USDT）、現貨與永續合約的差別（並回扣 Day 01 的原則：**兩者的資料 NEVER 混用**）、為什麼要先用 testnet。
- 工程實作：`data.binance.vision` 的 URL 結構與檔案格式（`spot/monthly/klines/{SYMBOL}/{INTERVAL}/...zip`），用 `asyncio` 併發下載並驗證 checksum；解壓後的欄位對映與型別轉換（官方 CSV 沒有標頭，欄位順序要查文件）。缺口偵測後用 `ccxt` 補最後幾天：`since` + `limit` 的翻頁邏輯與 off-by-one 陷阱、`asyncio.Semaphore` 控併發、指數退避重試、看 `X-MBX-USED-WEIGHT` 標頭決定要不要退讓。API key 用 `.env` 讀入，NEVER 硬寫；key 權限只開讀取與交易、NEVER 開提幣、綁 IP 白名單。
- 驗證：用 CoinGecko 免費層抽幾天的日線比對批次資料，確認欄位對映沒錯（實踐 Day 01 的「每個主來源都要有對照組」）。
- 今日交付物：`ingest/binance.py` 能回補任意交易對、任意時間範圍的 K 線——自動決定哪段走批次、哪段走 REST，中斷後可重跑不重複，並輸出兩個來源的比對結果。

**Day 04（2026-09-18）— 均線到底在均什麼？MA / SMA 的向量化實作與三個常見算錯的地方**
- 講什麼：移動平均是最基本的降噪工具；SMA 的定義、視窗長度怎麼選、它為什麼一定會落後。
- 交易概念補課：趨勢、黃金交叉與死亡交叉、以及**未來函數**——這是本系列第一次正式警告：用 `rolling()` 時預設是「包含當根」，如果你的訊號用當根收盤價卻假設能用當根開盤價成交，回測就假了。
- 工程實作：`df['close'].rolling(n).mean()` 的向量化寫法，並明確示範**為什麼不要寫 for loop**（附兩種寫法的 `%timeit` 對照）。三個算錯的地方：(1) 前 n-1 根是 NaN 該怎麼處理，(2) 資料有缺漏時 `rolling` 的視窗實際涵蓋了更長的時間，(3) 未來函數。用 `pandas-ta` 對照數值驗證自己算的是對的。
- 視覺化：Plotly 把 K 線與 SMA(20)／SMA(60) 疊圖，標出交叉點。
- 今日交付物：`indicators/ma.py` ＋ `tests/test_ma.py`（含缺漏資料與資料不足的邊界測試）。

**Day 05（2026-09-19）— SMA 反應太慢、訊號永遠慢半拍？換上 EMA 並看懂它的遞迴特性**
- 講什麼：EMA 給近期資料更高權重；平滑係數 α 與週期 n 的關係；EMA 為什麼「沒有真正的起始點」（初始值怎麼取會影響前幾十根）。
- 交易概念補課：平滑、延遲（lag）、遞迴指標的意思。
- 工程實作：EMA 是遞迴的（`ema[i]` 依賴 `ema[i-1]`），這是本系列第一個**不能直接向量化**的指標——先示範 `ewm()` 怎麼一行搞定，再解釋 `adjust=True` 與 `adjust=False` 算出來的數字為什麼不一樣、交易上該用哪一個。這裡埋下 Day 26 Numba 的伏筆。
- 視覺化：同一張圖比較 SMA(20) 與 EMA(20) 對一段急跌的反應速度。
- 今日交付物：`indicators/ema.py`，與 `pandas-ta` 數值誤差在 1e-9 以內。

**Day 06（2026-09-20）— 怎麼知道現在是漲太多還是跌太深？用 RSI 把動能量化成 0–100**
- 講什麼：RSI 的邏輯拆解——把漲跌幅分開平均、算成相對強度、壓縮到 0–100；為什麼是 14 週期；超買 70／超賣 30 是慣例而不是定律。
- 交易概念補課：動能、超買／超賣、背離。並且要講清楚一件事：**RSI 超買不代表要跌**，在強趨勢裡它可以貼著 80 走很久。指標是描述，不是預測。
- 工程實作：Wilder 平滑跟一般 EMA 的差別（α = 1/n 而非 2/(n+1)），這是自己實作 RSI 最常算錯的地方。用 `pandas-ta` 對照，並示範兩種寫法差多少。
- 視覺化：雙軸圖，上面 K 線、下面 RSI 與 70／30 水平線。
- 今日交付物：`indicators/rsi.py` ＋ 測試；三個指標統一成同樣的函式簽章（吃 DataFrame、回傳 Series），為 Day 15 的模組化鋪路。

**Day 07（2026-09-21）— 行情資料越存越多、查詢越來越慢？為什麼時序資料庫（TimescaleDB）才是對的容器**
- 講什麼：市場資料的特性——只增不改、幾乎都用時間範圍查、量隨時間線性成長。這三個特性剛好是 hypertable 分區的最佳場景。為什麼不用 CSV／parquet 檔案堆（跨檔案查詢與去重很痛）、為什麼不用純 PostgreSQL（缺時間分區與壓縮）、為什麼不用 InfluxDB（想用 SQL 而不是另一套查詢語言）。
- 交易概念補課：不同 timeframe 的資料要分表還是共表；為什麼 1 分鐘資料值得存（Day 09 之後會用到）。
- 工程實作：schema 設計（`symbol`, `timeframe`, `open_time`, OHLCV，複合主鍵防重複）；`create_hypertable`；用 `ON CONFLICT DO NOTHING` 做冪等寫入；continuous aggregate 讓 1m 自動聚合出 5m／1h（不用自己算，也不會算錯）；壓縮政策。用 `asyncpg` 搭配 `COPY` 批次寫入。
- 今日交付物：`storage/` 模組 ＋ migration，能把 Day 03 抓下來的資料入庫，重跑不會產生重複列。

**Day 08（2026-09-22）— 第一階段總結：把擷取、清洗、入庫串成一條每天自己跑的 Pipeline**
- 講什麼：把前六天的零件接成一條管線：排程 → 找出缺哪段 → 決定走批次還是 REST → 回補 → 清洗 → 入庫 → 驗證。重點是**冪等**與**可觀測**：跑兩次結果一樣，出錯知道是哪一段。
- 交易概念補課：資料品質對交易的意義——一根缺漏的 K 線可能讓你的均線算錯十天，而你不會收到任何錯誤訊息。
- 工程實作：缺漏偵測（用預期的時間序列跟實際的做 diff）、路由邏輯（缺口超過 N 天走 `data.binance.vision`，否則走 REST，實作 Day 03 的雙軌設計）、異常值處理（成交量為 0、價格跳動超過合理範圍）、去重、時區統一。用 `asyncio` 併發回補多個交易對。排程先用 cron，Day 27 換成容器內排程。
- 驗證：管線最後一步跑對照——抽樣跟 CoinGecko 或 CryptoDataDownload 比對，不一致就在報告裡標出來。
- 今日交付物：一支 `python -m quantbot.ingest.pipeline` 能把設定檔裡所有交易對補到最新，並輸出一份資料完整性報告（缺漏區間、異常值、對照組差異）。

### 第二階段｜微觀結構與特徵工程：解構市場（Day 09–15）
專案階段：從 OHLCV 這層往下挖。第一階段的三個指標任何看盤軟體都有，這段要做的是**別人的 TradingView 上沒有的特徵**——因為那些都得自己從 Tick 與掛單簿算。最後一天（Day 15）把散落的指標與特徵收斂成統一介面，交給第三階段的策略引擎當原料。

**Day 09（2026-09-23）— K 線把一分鐘壓成四個數字，中間發生的事呢？認識 Tick 與 L2 Order Book**
- 講什麼：回收 Day 02 埋的伏筆。一根 1 分鐘 K 線可能是 3 筆成交，也可能是 3000 筆；OHLCV 完全看不出差別。逐筆成交（Tick）與掛單簿（L2）各自補了什麼資訊。資料量級的現實：一天的 BTC tick 資料比一年的日線大好幾個數量級。
- 交易概念補課：Tick、買賣價差、掛單簿的五檔／二十檔、深度、taker 與 maker。
- 工程實作：用 WebSocket 訂閱 `@trade` 與 `@depth`；本地維護一份掛單簿快照（snapshot + incremental update 的合併邏輯，以及序號斷掉時要重新拉快照）；資料量控制——不要什麼都存，先想清楚要算什麼特徵再決定存什麼。
- 資料來源提醒：**歷史的 tick 與掛單簿不必自己錄**——`data.binance.vision` 有 `aggTrades` 與 `bookTicker` 的批次檔可下載，跟 Day 03 同一條路徑。WebSocket 負責的是「從現在起往前累積」，兩者要能在同一張表裡接得起來（時間戳與欄位定義 MUST 統一）。這也是本階段唯一不設對照組的資料——這層粒度只信交易所原生。
- 今日交付物：`ingest/stream.py` 能訂閱即時成交與掛單簿，並在斷線後自動重連、重取快照；`aggTrades` 歷史批次已入庫，與即時串流的資料在邊界處無縫接上。

**Day 10（2026-09-24）— 掛單簿買賣兩邊不對稱代表什麼？用 Order Book Imbalance 量化短線壓力**
- 講什麼：OBI 的直覺——買單掛得比賣單多，短時間內價格傾向往上；它的定義、計算深度該取幾檔、以及它衰減得很快（這是分鐘級以下的訊號，不要拿它做日線策略）。
- 交易概念補課：流動性、掛單不對稱、以及一個重要的提醒——掛單可以撤，所以 OBI 有被操縱的空間（spoofing）。
- 工程實作：從 Day 09 的掛單簿快照計算 OBI；不同深度（5／10／20 檔）的結果差異；用 numpy 向量化算整段歷史；把它跟未來 N 秒的報酬做相關性分析，實際檢查它到底有沒有預測力（這是本系列第一次教讀者**驗證一個特徵值不值得用**）。

**Day 11（2026-09-25）— 均價要用哪個？VWAP 與成交量加權的資金流視角**
- 講什麼：算術平均把 1 顆 BTC 的成交跟 100 顆的成交當成一樣重要，這顯然不對。VWAP 用成交量加權，代表「市場的平均成本」。日內 VWAP（每天重置）與滾動 VWAP 的差別與各自用途。
- 交易概念補課：VWAP 為什麼是機構的參考基準；價格在 VWAP 之上／之下的意義；資金流的概念。
- 工程實作：向量化實作（`(price * volume).cumsum() / volume.cumsum()`）；日內重置怎麼用 `groupby` 做；用典型價 `(H+L+C)/3` 而非收盤價的理由；VWAP 標準差通道。

**Day 12（2026-09-26）— 同樣的價格，有時候很危險有時候沒事：用交易活躍度定義市場的節奏**
- 講什麼：市場有「心跳」——同樣漲 1%，在冷清時段和活躍時段的意義完全不同。用成交筆數、成交量、波動率三個角度量化活躍度，並做出「相對於自己平常」的標準化指標（z-score），因為絕對值在不同交易對之間不可比。
- 交易概念補課：波動率的意思與計算方式（已實現波動率）；為什麼加密貨幣 24/7 還是有明顯的時段節奏（亞洲／歐洲／美國時段）。
- 工程實作：滾動 z-score 的向量化；用 `groupby(hour)` 做時段基準；ATR（真實波動幅度）當作波動率的另一種算法——它會在 Day 24 用來決定停損距離。
- 視覺化：以小時為軸的活躍度熱力圖。
- 今日交付物：`features/activity.py`，輸出可以直接當策略過濾條件的活躍度分數。

**Day 13（2026-09-27）— 突破了卻馬上被打回來？從流動性擺盪找出假突破的資料特徵**
- 講什麼：假突破是新手最常虧錢的地方。用資料的角度看，真突破與假突破在**成交量、掛單簿變化、突破後的回撤速度**上有可觀察的差異。定義一個 Liquidity Swing 特徵：價格衝破前高的同時，掛單簿另一側的流動性是被吃掉還是被撤走。
- 交易概念補課：突破、假突破、停損獵殺（為什麼前高前低附近特別容易發生）。
- 工程實作：前高／前低的滾動計算（`rolling().max()` 的 shift 處理，避免用到當根）；突破事件的標記；用歷史資料統計真假突破的比例與各自的特徵分布。這裡要示範**事件式特徵**怎麼跟時間序列特徵接在一起。

**Day 14（2026-09-28）— 支撐壓力線可以不用手畫嗎？用 Volume Profile 自動找出籌碼密集區**
- 講什麼：傳統畫線很主觀。Volume Profile 換一個維度——不看時間軸上的成交量，看**價格軸上的成交量分布**。成交量堆積最多的價格就是多數人的成本區，那裡自然形成支撐或壓力。
- 交易概念補課：支撐與壓力、籌碼密集區、POC、價值區間（Value Area 70%）。
- 工程實作：把成交量按價格分桶（`np.histogram` 或 `pd.cut`）；用 K 線資料近似 vs 用 tick 資料精算的差別；POC 與 Value Area 的計算；滾動視窗版本（過去 N 天的 profile）。

**Day 15（2026-09-29）— 第二階段總結：把指標從散落的函式收斂成可重用的 feature 模組**
- 講什麼：到目前為止手上有八個東西——第一階段的三個指標（MA／EMA／RSI）與這一階段的五個特徵（OBI、VWAP、活躍度、流動性擺盪、Volume Profile），各自的簽章、輸入輸出、參數命名都不太一樣。這天做的事很工程：**定義統一介面**，讓後面寫策略時可以宣告式地組合，而不是每次手動串。
- 交易概念補課：特徵工程在量化裡的地位——策略邏輯常常只有十行，八成的工作在特徵。

### 第三階段｜策略開發與回測：量化實戰（Day 16–22）
專案階段：從「有特徵」到「有策略引擎」再到「知道組合出來的策略到底行不行」。這段建立本系列的核心產出——**一個讓使用者自己排列組合的策略積木庫**——並且立刻補上它必須配套的安全鎖（Day 21）。

> **這一階段的設計主張：策略不是「一個 class」，是「一組可以互換的積木」。** 如果每個策略都是獨立的 class，三個策略就有三份重複的「算特徵、判斷條件、決定部位」邏輯，而且使用者想試「這個策略的進場條件配那個策略的出場條件」時完全沒辦法。積木化之後，新策略的成本降到一個設定檔——但同時也讓「亂試一通」變得太容易，所以 Day 21 是這個設計的必要配套，不是可選的加分題。

**Day 16（2026-09-30）— 每寫一個策略就複製貼上一份程式？把策略拆成可以互相組合的積木**
- 講什麼：先看清楚問題（上面的設計主張），再切出兩層抽象——**條件（Condition）**與**組合方式**。一個策略＝三組條件（進場、出場、過濾）＋組合運算。這是整個 `quantbot` 最關鍵的一天。
- 交易概念補課：訊號、進場與出場、部位（做多 +1／空手 0／做空 -1）；為什麼「進場」「出場」「過濾」是三種不同角色不能混為一談——過濾條件不會讓你進場，只會否決進場；以及為什麼「訊號」與「部位大小」要分開（部位大小是 Day 24 的事，也會做成積木）。
- 工程實作：`Condition` 協定（吃 DataFrame、回傳 boolean Series）；內建基礎條件（交叉、閾值、區間、排名、事件觸發）；用 `__and__` / `__or__` / `__invert__` 讓條件能直接用運算子組合成條件樹；`required_features` 從條件樹**自動推導**（使用者不必手動宣告，也就不會漏）；warm-up 期由條件樹的最長視窗自動算出。
- **訊號 shift 統一寫進引擎**：把「用第 t 根的資訊、第 t+1 根成交」做成引擎行為，而不是靠每個策略自己記得。積木化之後策略數量會暴增，靠人記得一定會漏——這是防未來函數最有效的一招。
- 今日交付物：`strategies/blocks.py` ＋ `strategies/engine.py`；一個什麼都不做的 `BuyAndHold` 當基準（後面所有組合都要贏過它才有意義）；一組測試證明組合運算子的行為正確。

**Day 17（2026-10-01）— 第一個組合：先用 Python 寫出趨勢跟隨的邏輯，再把它拆成積木**
- 講什麼：走完整條路徑。先用最直白的 Python 寫出「EMA 快慢線交叉、RSI 過濾掉追高」的判斷邏輯，講清楚每個條件在防什麼問題——**這一步不能跳過**，否則讀者只學會填設定檔、不知道自己在填什麼。邏輯確認正確後，再示範怎麼拆成 Day 16 的積木，最後寫成 YAML 並加上載入器。
- 交易概念補課：趨勢跟隨的特性——勝率低但賠率高，大部分交易小賠、少數幾筆大賺；所以**不能用勝率評估這種策略**。
- 工程實作：交叉條件的正確寫法（只在交叉當根觸發，不是整段都成立）；過濾條件與進場條件的結合；YAML schema 設計與 `pydantic` 驗證（設定寫錯要在載入時就報錯，不要跑到一半才炸）；載入器把設定檔轉成條件樹。
- **引擎正確性的證明**：同一個策略用三種寫法（純 Python／積木運算子／YAML）產生**逐根完全相同**的訊號序列。這個測試比任何說明都有力。
- 今日交付物：`strategies/configs/trend_ema_rsi.yaml` 能載入並跑出訊號；三種寫法等價（有測試保證）。

**Day 18（2026-10-02）— 換一組積木就換一種風格：均值回歸與動能爆發**
- 講什麼：引擎存在之後，新策略的成本就是一個設定檔。用兩個哲學截然相反的策略證明這件事——均值回歸（價格顯著偏離 VWAP 且 OBI 顯示反向壓力）與動能爆發（活躍度 z-score 爆量且不是假突破）。重點不在策略本身，在於**同一組積木能不能表達完全不同的交易哲學**；如果不能，就是 Day 16 的抽象切錯了，要回頭改。
- 交易概念補課：均值回歸的特性（勝率高但賠率低，最怕回歸失敗變成趨勢，所以停損比什麼都重要）；動能爆發是事件驅動、訊號稀疏，一個月可能只有幾次，樣本數少會讓回測的統計意義薄弱（這條伏筆 Day 21 收）；趨勢與均值回歸為什麼不該同時開，以及市場狀態（regime）的概念。
- 工程實作：這兩個策略各自逼出的新積木——最大持有時間（超過 N 根還沒回歸就認錯出場）與冷卻期（避免同一波行情重複進場）。重點是**把它們加進積木庫而不是寫死在策略裡**，這是判斷抽象有沒有做對的實際檢驗。另外處理進出場條件不對稱（進場嚴格、出場寬鬆）在設定檔怎麼表達。
- 今日交付物：三個策略都是設定檔；積木庫補上時間類條件；跑一次「Day 17 的進場條件配 Day 18 的出場條件」，證明真的可以交叉組合。

**Day 19（2026-10-03）— 策略在腦中很賺，怎麼證明？用 VectorBT 做向量化歷史回測**
- 講什麼：回測是什麼、以及它到底能證明什麼（過去有效）跟不能證明什麼（未來有效）。VectorBT 為什麼快（整段訊號一次算完，不是逐根模擬），Backtrader 這類事件驅動引擎的優缺點對照與適用時機。
- 交易概念補課：回測、樣本內與樣本外、過度擬合。**最重要的一段**：回測作弊的四種常見形式——未來函數、倖存者偏差、用未來資料調參數、參數挖礦。逐一給出程式碼層級的檢查方法。後兩種在積木化之後特別容易發生，Day 21 專門處理。
- 工程實作：把引擎產出的訊號餵進 VectorBT；設定初始資金與部位；跑出第一份績效數字。回收 Day 04 的未來函數伏筆——用一個**故意關掉引擎 shift** 的版本示範報酬會離譜到什麼程度，讓讀者記住 Day 16 那個設計在擋什麼。
- 今日交付物：`backtest/runner.py`，任何設定檔都能跑完並輸出績效摘要。

**Day 20（2026-10-04）— 回測賺 300%、實單卻賠錢？把滑價與手續費加回去看真相**
- 講什麼：理想回測假設你能用收盤價成交、不用付錢、想買多少有多少——三個假設都是假的。逐一把成本加回去，看績效怎麼縮水。
- 交易概念補課：手續費（maker／taker 差別、VIP 等級、用 BNB 折抵）；滑價的來源（價差、市場衝擊、延遲）；為什麼交易越頻繁的策略對成本越敏感——交易次數乘上單次成本才是真正的損耗，而積木組合很容易不小心組出一個交易過於頻繁的策略。
- 工程實作：在 VectorBT 設定 `fees` 與 `slippage`；用 Day 09 的掛單簿資料估算真實滑價而不是拍腦袋給 0.05%；計算「成本佔毛利多少百分比」這個關鍵比率；敏感度分析——手續費從 0.02% 到 0.1%，策略在哪一點由賺轉賠。
- 視覺化：加成本前後的權益曲線疊圖，這張圖是全系列最有說服力的一張。
- 今日交付物：成本模型接進 `backtest/`；三個策略的加成本結果；誠實記錄哪些在真實成本下不成立。

**Day 21（2026-10-05）— 積木能排出幾百種組合，那就全跑一遍挑最好的？這正是你會虧錢的地方**
- 講什麼：這天是組合式框架**必須**附帶的安全鎖。積木化之後跑幾百個組合只要幾分鐘——問題是「跑 500 個、挑回測最漂亮的那一個」在統計上等於自欺。這天講清楚為什麼會這樣、以及該怎麼做才對。
- 交易概念補課：多重比較問題（試得越多，純靠運氣冒出漂亮結果的機率越高）；樣本內與樣本外；walk-forward 驗證；參數挖礦與過度擬合的關係。順便收 Day 18 的伏筆——訊號稀疏的策略樣本數本來就少，在組合搜尋裡最容易產生假陽性。
- **關鍵示範（本篇的核心）**：用隨機生成的假價格序列（或把真實報酬順序打亂）跑同一套組合搜尋，看你能「找到」多漂亮的策略。讀者會親眼看到，在**完全沒有訊號的資料上**，搜尋幾百個組合照樣能挖出夏普值很好看的「策略」。這張圖比任何說教都有效。
- 工程實作：組合空間怎麼定義（不是全排列——要用領域知識剪枝，並說明為什麼「趨勢進場配均值回歸出場」多數時候不該進搜尋空間）；批次回測的執行與結果收集；樣本內外切分與 walk-forward 實作；用試驗次數對夏普值做折價（deflated Sharpe 的直覺，不推導公式）；**把「這個結果試了幾次才得到」記錄進結果表——沒有記錄試驗次數的回測結果一律不可信**。
- 今日交付物：`backtest/search.py` 能跑組合搜尋並輸出含試驗次數與樣本外表現的結果表；一份「隨機資料也能挖出好策略」的示範 notebook。

**Day 22（2026-10-06）— 第三階段總結：讀懂權益曲線，以及怎麼公平比較幾十個策略**
- 講什麼：總報酬率是最沒用的指標。真正要看的是**最大回撤**（你能不能撐過去）、**夏普／索提諾比率**（承擔的風險划不划算）、**勝率與賠率的組合**（單看勝率會誤導）、**交易次數**（樣本數夠不夠）。每個指標解釋「它在防你犯什麼錯」。接著處理組合式框架帶來的新問題：**幾十個策略要怎麼並排比較才公平**——同一段資料、同一組成本假設、同樣標注試驗次數與樣本外表現。
- 交易概念補課：權益曲線怎麼看（斜率、回撤深度、回撤持續時間，最後一項常被忽略但最折磨人）；為什麼 60% 勝率的策略可能是賠錢的；為什麼「排行榜第一名」不等於「最該上線的那一個」。
- 工程實作：績效報表模組——單一策略的一頁式報告（權益曲線、回撤區間、月報酬熱力圖、單筆交易分布），以及**多策略比較視圖**（績效矩陣、權益曲線疊圖、相關性熱力圖——高度相關的策略同時上線等於加大同一個賭注）。用 Day 16 的 `BuyAndHold` 當基準算超額報酬。
- 今日交付物：`backtest/report.py`，單策略與批次搜尋結果都能自動產出 HTML 報告。

### 第四階段｜系統穩定性與風險控管：邁向自動化（Day 23–30）
專案階段：從「回測能跑」到「真的掛在雲端跑」。這段全部是工程題，也是工程師最有優勢的一段。

**Day 23（2026-10-07）— 凌晨三點 API 斷線、機器人卡死？用防禦性設計讓它自己活下來**
- 講什麼：交易程式的失敗模式清單——網路斷、API 逾時、限流、交易所回 5xx、WebSocket 靜默斷線（沒有錯誤但也沒有資料）、下單回報遺失。每一種對應的處理策略不同，不能全部 `except Exception: pass`。
- 交易概念補課：最危險的不是「掛掉」，是「以為自己有部位其實沒有」或反之。狀態不一致比停機更糟。
- 工程實作：分層例外處理（可重試 vs 不可重試）；指數退避 + jitter；WebSocket 心跳與逾時重連；斷路器（連續失敗就停止交易並告警）；下單的冪等性（用 `clientOrderId` 避免重複下單）；啟動時與交易所對帳，以交易所的部位為準而不是本地狀態。
- 今日交付物：`execution/` 的下單封裝，具備重試、冪等、對帳；用 testnet 實際測試斷線恢復。

**Day 24（2026-10-08）— 一次該下多少錢？從固定比例到凱利公式的部位管理**
- 講什麼：策略決定「買不買」，風控決定「買多少」——後者對長期結果的影響往往更大。從最簡單的固定金額，到固定比例，到用 ATR 決定停損距離再反推部位（風險平價的雛形），最後講凱利公式。
- 交易概念補課：部位管理、槓桿、爆倉；凱利公式的推導直覺（最大化長期複利成長率）與它的致命問題——**它假設你知道真實的勝率與賠率，而你不知道**，所以實務上一律用分數凱利（1/4 到 1/2）。破產風險與連續虧損的模擬。
- 工程實作：`risk/sizing.py` 實作四種部位計算方式，**並且做成跟 Day 16 同樣形式的可插拔積木**——設定檔裡換一行就能換 sizing 策略，才能公平比較「同一個訊號配不同 sizing」；拿 Day 20–21 跑出來的加成本回測結果做蒙地卡羅模擬，比較不同 sizing 下的權益曲線分布與破產機率；加上硬性上限（單筆最大風險、總曝險上限、單日最大虧損就停止交易），這些上限是引擎層強制的，NEVER 交給策略設定檔覆寫。
- 視覺化：同一策略在不同 sizing 下的 1000 條模擬權益曲線。
- 今日交付物：`risk/` 模組接進回測，所有策略重跑一次帶風控的版本。

**Day 25（2026-10-09）— 機器人在雲端跑，你怎麼知道它還活著？用 Telegram 建立回報與告警**
- 講什麼：無人值守系統的第一原則——**沒有消息不等於好消息**。設計三個層級的通知：心跳（每天一次「我還活著」）、事件（有交易發生）、告警（出事了，需要你介入）。告警疲勞是真的，設計時要克制。
- 交易概念補課：哪些事件真的需要半夜叫醒你（連續虧損超過閾值、部位與交易所不一致、資金異常），哪些不用（單筆停損）。
- 工程實作：Telegram Bot 建立與 token 管理；非同步發送不阻塞主迴圈；訊息去重與速率限制；用 Bot 做**雙向控制**——傳指令查詢目前部位、緊急平倉、暫停交易（這是 human-in-the-loop 的閘門）。
- 今日交付物：`monitor/telegram.py`，手機收得到心跳與告警，並能下 `/status` 與 `/pause` 指令。

**Day 26（2026-10-10）— 指標算一次要好幾秒、來不及下單？用 Numba 把熱點函式加速**
- 講什麼：先講**不要過早最佳化**——先量測再優化。用 `cProfile` 找出真正的熱點，通常會發現是那幾個沒辦法向量化的遞迴指標（回收 Day 05 的伏筆）。
- 交易概念補課：延遲對不同策略的意義——日線策略慢 3 秒沒差，分鐘級策略慢 3 秒可能整個訊號就沒了。先確認你的策略需不需要這個優化。
- 工程實作：`cProfile` 與 `line_profiler` 量測；`@njit` 改寫 EMA 與 RSI 的迴圈版本，跟 pandas 版本比較速度與數值一致性；`cache=True` 避免每次啟動重新編譯；Numba 的限制（不支援 pandas 物件、型別要穩定）；什麼時候該用 numpy 廣播而不是 Numba。附完整的 benchmark 數字。
- 今日交付物：熱點函式加速後的 benchmark 對照表，且數值與原版一致（有測試保證）。

**Day 27（2026-10-11）— 本機跑得好好的，上雲就掛？用 Docker 把機器人打包部署到 VPS**
- 講什麼：容器化解決的是「環境一致」與「掛掉自動重啟」。多階段建置縮小映像檔；`docker compose` 把交易機器人、TimescaleDB、監控三個服務接起來。
- 交易概念補課：VPS 位置會影響延遲（離交易所機房越近越好）；但對本系列的策略頻率來說，穩定性比延遲重要得多——不要為了幾毫秒選一個會斷線的機房。
- 工程實作：多階段 Dockerfile；`.dockerignore` 避免把 `.env` 打包進去；secrets 用環境變數注入而非寫進映像檔；`restart: unless-stopped`；healthcheck 與 `depends_on` 的正確用法；volume 持久化 DB；時區與 locale 設定（NTP 對時對交易系統是必要的）；部署到 VPS 的完整步驟與防火牆設定。
- 今日交付物：`docker/` 目錄完備，一行 `docker compose up -d` 在 VPS 上跑起整套系統（先接 testnet）。

**Day 28（2026-10-12）— 策略虧錢了，但你說不出是哪裡出錯？用結構化交易日誌還原每一筆決策**
- 講什麼：交易系統的日誌跟一般服務不同——你要能回答「三天前那筆單為什麼會下」。這需要記錄的不只是「下了什麼單」，而是**當下的完整決策脈絡**：那一刻的特徵值、觸發了哪個條件、部位計算的輸入與輸出。
- 交易概念補課：交易日誌在人工交易裡是紀律工具，在自動交易裡是除錯工具；兩者要記的東西不一樣。
- 工程實作：結構化日誌（`structlog` 輸出 JSON）；決策快照寫進 TimescaleDB 而不只是檔案（才查得動）；correlation id 串起「訊號 → 風控 → 下單 → 成交」整條鏈；區分交易日誌與系統日誌；日誌輪替與保存策略。示範一次實際的除錯：從一筆異常交易反查到某個特徵在資料缺漏時算出了錯誤值。
- **積木化讓這件事更重要也更好做**：日誌 MUST 記錄「用了哪個設定檔、哪個版本、條件樹裡哪幾個節點成立」。因為策略是宣告式的，你可以把整棵條件樹連同各節點的當下真假值一起存下來——這是手寫策略做不到的，出事時能直接看到是哪一個積木判斷錯。
- 今日交付物：`monitor/journal.py`，每筆交易都能用一句 SQL 撈出完整決策脈絡。

**Day 29（2026-10-13）— 遇到閃崩、交易所停機、資料斷檔怎麼辦？把極端行情當成邊緣案例來測**
- 講什麼：正常行情下能跑不代表能上線。列出交易系統的極端案例清單並逐一測試：價格瞬間跳動 20%、成交量歸零、交易所維護、掛單簿只剩一邊、下單被拒（餘額不足／超過限額）、部分成交、系統時間跳動。
- 交易概念補課：閃崩、流動性枯竭；為什麼「停損單在閃崩時可能以離譜價位成交」；極端行情下最好的策略常常是**什麼都不做**。
- 工程實作：用歷史上的真實極端事件當測試資料（找出資料集裡的幾次大跌）；用 `pytest` 建構故障注入測試（mock 交易所回傳異常）；熔斷機制——偵測到異常市況就自動暫停交易並告警；資料合理性檢查放在管線最前面（價格為 0 或跳動超過閾值就拒絕處理）。
- 今日交付物：`tests/test_edge_cases.py` 覆蓋清單上每一個案例；系統具備自動熔斷。

**Day 30（2026-10-14）— 完賽總結：自動化替你執行了哪些紀律，以及這套系統的下一步**
- 講什麼：分兩段。前半段回答「工程師視角下，自動化到底贏在哪」——不是贏在演算法聰明，是贏在**它會嚴格執行你冷靜時訂下的規則**：不會因為虧了三筆就放大部位、不會因為捨不得就把停損往下挪、不會半夜看到暴跌就恐慌平倉。人性的那些弱點，在你把規則寫成程式碼的那一刻就被隔離了；反過來說，這也意味著**規則寫錯時它會忠實地一路錯到底**，所以前面 29 天在測試與監控上花的功夫才是真正的護欄。
- 後半段回顧這 30 天蓋出來的東西（資料管線 → 特徵庫 → **策略積木庫與組合引擎** → 回測與組合搜尋 → 風控 → 部署 → 監控）。這裡要把積木庫的故事收完：你手上不是三個策略，是一套能表達策略的語言——**而語言的價值取決於你有沒有能力判斷自己說出來的話是不是廢話**，這正是 Day 21 存在的理由。接著給出演化路徑：多交易對與投資組合配置、市場狀態偵測與策略切換、參數的 walk-forward 驗證、機器學習做特徵組合、從現貨走向合約與跨市場套利。每個方向講清楚**前置條件是什麼**，避免讀者跳級。
- 也回收 Day 01 的資料來源版圖：這 30 天全程只用了免費的交易所原生資料，現在可以談**什麼時候值得往外擴**——做資金費率套利或想用清算熱力圖當特徵，就接 CoinGlass（V4 API，深度歷史需 Pro）；要跨多家交易所重建多年 L2 掛單簿，才輪到 Tardis.dev 那類機構級來源；要做 DeFi 或 smart money 相關策略，才進 Dune／Nansen／Glassnode／DefiLlama 的領域。每一個都要先問「這筆錢買到的資料，會改變我哪一個決策」。

### 沿用全站規範

本系列完全沿用 [`blog-writing-style`](../rules/blog-writing-style.md) 的所有硬性規則，包含但不限於：

- **標題層級從 h2（`##`）開始**，子節用 h3、h4；正文 NEVER 出現 h1（頁面 h1 由模板從 frontmatter `title` 渲染）。程式碼區塊內的 `#` 不受此限。

  - **本系列補充的死語**（沿用同一條原則：能用樸素日常的講法就不要用老派成語）：

### 本系列專屬規範

以下是量化交易主題特有的硬性要求，撰稿時 **MUST** 逐條檢查：

**程式碼品質**

- **向量化是不可妥協的**。NEVER 用 for loop 遍歷 K 線。真的必須遞迴（EMA、RSI 的 Wilder 平滑）時，**MUST** 明確說明「這裡為什麼不能向量化」，並示範 `ewm()` 或 Numba 的正確做法。

**資料來源**
